大模型的上下文（Context Window）

60 秒速读 大模型的「上下文」= 单次请求里模型能「看到」的全部文本，包含系统提示、历史对话、工具结果、图片、文件、本轮的输出 token。它不是训练数据，而是模型的「工作内存」。窗口越大能装的越多，但装得多不等于记得好——超过一定长度后，准确率反而会下降（业内叫 context rot）。

学习目标

  • 能用一句话说清「上下文窗口」和「训练数据」的区别
  • 能列出构成一次请求上下文的 5 类内容（system prompt / messages / tool results / extended thinking / output）
  • 能解释「context rot」是什么、为什么窗口不是越大越好
  • 能给出至少 2 个把「上下文工程」落到实处的做法（缓存、压缩、截断）

核心问题

上下文窗口和「模型的知识」是一回事吗？
不是。模型的「知识」来自训练时见过的海量语料，这些权重是**冻结**的，不会因为你在对话里说了什么而改变。上下文窗口是模型在**这一次生成时**能参考的全部内容——更像是它当下的「工作台面」，而不是它的「记忆」。这张台面大小是有限的，按 token 算。
为什么窗口不是越大越好？
Anthropic 在 2025 年的上下文工程指南里专门用一个词形容这种现象：context rot（上下文腐烂）——token 越多，模型对细节的召回和推理准确率反而会下降。可能的原因包括：信息淹没关键信号、长程依赖变弱、注意力分散。所以「把能塞的全塞进去」是常见误区，**「只放当下需要的」** 才是工程目标。
系统提示和对话历史都算上下文吗？
都算。一次 API 请求里，模型要看的全部内容包括：system prompt（系统提示，定基调）、messages 数组里的全部历史轮次和工具返回结果、tool definitions（工具的 schema 描述本身也占 token）、extended thinking 的思考块（如果启用了思考）、以及本轮模型正在生成的输出 token。Anthropic 的官方文档明确说「everything in the request counts toward the context window」。
上下文满了会怎样？
三种处理方式：① 直接报错（OpenAI 默认行为，要求你手动管理）；② 自动截断（OpenAI Responses API 设 truncation=auto 会从最早的消息开始丢）；③ 服务端压缩（Anthropic 把 server-side compaction 作为长对话和 Agent 场景的主要策略，本质上是把早期内容总结成更短的摘要）。

结构化解释

是什么

「上下文窗口」（Context Window）是语言模型在单次生成时能引用的全部文本上限，按 token 计数。它和模型的训练数据不同——训练数据是冻结的「记忆」，上下文窗口是当下的「工作台」。Anthropic 给出的精确定义是：「the context window refers to all the text a language model can reference when generating a response, including the response itself」。

为什么

上下文窗口是 LLM 推理的根本约束——它决定了「一次能喂给模型多少信息」。窗口小，老长文档塞不下；窗口大，又要付出成本（每次请求按 token 计费）和质量代价（context rot）。所以从工程角度看，「上下文」不只是技术参数，更是 LLM 应用的核心资源——怎么把**当下最相关**的信息塞进去，本身就是一门工程学科，叫 context engineering（上下文工程）。

怎么工作（一次请求里都装了什么）

  1. 系统提示（system prompt / developer message）：定角色、定规则、定输出格式
  2. 历史消息（messages）：多轮对话的 user / assistant 交替
  3. 工具结果（tool results）：Agent 调用 API/查数据库/读文件的返回内容
  4. 工具 schema 本身：可调用工具的描述、参数定义也占 token
  5. 扩展思考（extended thinking）：如果模型有「思考块」，那部分 token 也计入窗口
  6. 本轮输出：连模型自己这次说的话也算进去（生成到第 N 个 token 时，前 N 个都已经「在」上下文里）

对当前主流模型来说，窗口大致分两档：200K token（如 Claude Sonnet 4.5、GPT-4o 类）和 1M token（如 Claude Opus 4.6+、Sonnet 4.6、Sonnet 5）。1M 已经是默认上限，不需要特殊请求头。

应用案例

案例：长会议纪要 Agent

场景：让 Agent 读一份 4 小时会议的转录稿（约 6 万字、~150K token），输出结构化纪要：决议、待办、责任人、时间。

  1. 把转录稿按章节切片（每片 10K token），作为「文件」传给模型。
  2. 系统提示里写明纪要的字段格式（决议 / 待办 / 责任人 / 截止）。
  3. 第一轮让模型对每片输出要点（每片 ~2K token），累计放进 messages。
  4. 第二轮让模型把所有要点合并去重，输出最终纪要。

这里几个上下文工程的细节都体现了：

  • 不是一次性把全文塞进去（避免 context rot），而是分片+摘要。
  • 工具结果占 token，所以每片只保留关键句，不留冗余。
  • 系统提示要短而明确，否则它就吃掉了大量预算。
  • 如果开启 prompt caching，系统提示和工具 schema 是天然命中缓存的，复用越多越省钱。

概念辨析

邻近概念 与「上下文」的区别 一句话判定
训练数据 / 知识 权重里的世界，写死在模型参数里 「它的记忆」 vs 「它桌上摊开的纸」
会话状态（conversation state） 是客户端/服务端管理「消息列表」的方式；上下文窗口是这份列表能装多大 「会话」是流程概念，「上下文」是容量概念
Prompt 是上下文的一部分（系统提示 + 用户输入），不是全部 「提示」是输入面，「上下文」是整个工作面
RAG（检索增强生成） RAG 是一种「按需把相关片段塞进上下文」的工程手段 「上下文」是被装的对象，「RAG」是往里装东西的方法

自测题

1.【单选】下面哪一项不计入一次请求的上下文窗口？
答案：D。模型在预训练阶段见过的语料不进上下文窗口，只进权重。
  1. 系统提示
  2. 工具 schema 定义
  3. 本轮模型自己生成的输出 token
  4. 模型预训练时见过的所有网页
2.【判断】上下文窗口越大，模型回答质量一定越好。
答案：错误。窗口越大能装的信息越多，但装得多不等于用得好——Anthropic 把这种「长上下文准确率反而下降」的现象叫做 context rot。实践上更看重「塞什么」而不是「能塞多少」。
3.【简答】Agent 场景下，工具调用结果会怎样影响上下文窗口？
答案：工具返回的内容会作为新的 tool_result 消息进入 messages 数组，全部计入上下文窗口。如果工具返回的是大文档（日志、长网页、表格），会迅速吃掉预算。所以工程上一般要：① 在工具侧先做摘要/切片；② 给大结果单独存到向量库，需要时按需检索。
4.【开放】请给一个具体例子，说明什么是「上下文工程」。
参考思路：把一个 200 页的产品手册塞给模型做客服问答——朴素做法是「每次提问都把整本手册塞进上下文」，但窗口会爆、还引发 context rot。上下文工程的做法是：① 把手册拆成段落做向量检索，② 只把跟当前问题最相关的 3-5 段作为上下文，③ 系统提示里强调「只能基于下面提供的资料回答，不知道就说不知道」。
