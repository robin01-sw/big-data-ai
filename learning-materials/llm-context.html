大模型的上下文（LLM Context）

60 秒速读 「上下文」是 LLM 一次推理能看见的全部输入（系统提示 + 历史 + 工具结果 + 检索文档拼接），按 token 计量且有上限。窗口大不等于有效长——context rot 与 Lost-in-the-Middle 让填满的窗口失效。
💡 通俗理解 本段由 AI 辅助整理，本人已阅读并核查。

一个常见误区是以为上下文就是聊天记录、越长越好。实际上，跟 AI 说话像跟一个记性不太好的人打电话——话越多、越啰嗦，它反而越抓不住重点，说过的还容易忘。

所以更有效的做法是：只把最要紧的事说清楚，旧的无用记录能省就省，重点永远放最前面讲。

学习目标

  • 能区分「上下文窗口大小」和「有效上下文长度」
  • 能用一句话讲清 context rot 与 Lost-in-the-Middle 的成因
  • 能解释 prompt caching 为什么能既省钱又加速
  • 能说出 Agent 工程里上下文管理的三条常见策略

核心问题

上下文窗口是按字符还是按 token 计算？
按 token 计算。一个 token 大约是 0.75 个英文单词，或 1 个中文字符的一半左右（中文通常 1~2 字 = 1 token）。OpenAI 的官方 Tokenizer 工具可以直接可视化任何一段文本会被切成多少 token。[1]
窗口越大越好吗？为什么「1M 上下文」听着厉害，实际不一定？
不一定。Chroma Research 在 2025 年的「Context Rot」研究中测了 18 个主流模型，发现 所有模型在窗口接近填满时都会出现性能显著下滑，并且表现出来的下滑程度和模型规模、版本都没有稳定关系——名义 1M 的窗口并不等于「1M 都好用」。[2]
Lost-in-the-Middle 是什么？
Liu 等人在 2023 年的 ACL 论文里首次系统化发现：把关键信息放在上下文中间位置时，模型回忆的准确率明显低于放在开头或结尾。后来多项研究复现了这一结论，已成为长上下文设计的常识反面案例。[3]
上下文工程（Context Engineering）和提示工程（Prompt Engineering）是什么关系？
Anthropic 在 2025 年的《Effective context engineering for AI agents》一文里把这两者明确区分：Prompt Engineering 关注「写好一条指令」；Context Engineering 关注「在上下文窗口有限、注意力稀缺的前提下，决定每轮应该把什么信息放进去」——是 Agent 工程的更宏观框架。[4]

结构化解释

理解「上下文」需要把握四件事：

  1. 它是一个有上限的工作记忆。LLM 没有持久的记忆，每次调用能「看见」的输入是有限的——这个上限就是上下文窗口，以 token 计数。GPT-4 原始 8K、Claude Sonnet 4 200K、Claude Sonnet 4.5 1M，名义数字一直在涨，但「有多大」不等于「实际能稳定处理多大」。
  2. 真正进窗口的，是系统提示 + 历史消息 + 工具结果 + 检索文档的拼接。你在 WorkBuddy 里和 Agent 的整轮对话，加上它调用工具返回的内容，全部都会按出现顺序拼成一条输入流。
  3. 有效长度远小于名义长度。Chroma Research 测出的 context rot 现象，与模型是否最新、是否大模型都没有可靠的相关性，唯一稳定相关的是「距离窗口上限越近，表现越差」。[2]
  4. 位置重要，中间危险。Lost-in-the-Middle 现象已被多项独立研究复现，关键信息要尽量放开始或结尾，避免埋在中间。[3]

一组常见的工程缓解策略

  • 截断 + 摘要：超出窗口的历史用 LLM 自己总结成短文本再回填。
  • RAG 检索：把知识从上下文外移到向量数据库，每次只取最相关的 top-k 塞进窗口。
  • Prompt caching：把不会变的前缀（系统提示 + 大文档）缓存，下次重复利用，OpenAI/Anthropic 都明确支持，并能同时省时间和省钱（命中时降本约 10 倍、加速 ~5x）。[5]
  • 分层/分块：把任务拆成多轮，每轮窗口独立，让模型在「新鲜小上下文」里工作。
一句话记住 「上下文窗口」是 LLM 的工作记忆，有大小、有顺序、有效长度小于名义长度—— 把正确的信息放在正确的位置，比单纯追求「更大」更重要。

应用案例

案例 1：客服 Agent 的对话记忆管理

一个客服 Agent 单次会话可能积累 50+ 轮消息、10+ 次工具调用结果，很容易撞到 64K 窗口上限。生产实践通常做：

  • 把系统提示 + 知识库长文档用 prompt caching 缓存，每次都重用前缀；
  • 对话历史每 5 轮做一次 LLM 摘要，旧轮摘要替代原文；
  • 工具结果超过 N 行时只保留首尾 + 中间计数「...(省略 200 行)...」。

这就是典型的「上下文工程」——不是把窗口买大，而是让每次请求的上下文「恰到好处」。[4]

案例 2：RAG 系统如何「借用」上下文

RAG 的核心思路是把知识从上下文「外移」出去：把整本手册存在向量库里，每次只把用户问题最相关的 5 段放进上下文窗口。窗口本身就是有限的，靠外置检索补足。这条路径现在成了企业知识库 Agent 的标配。

概念辨析 / 使用边界

易混项 正解
「窗口大小」=「有效长度」 二者不等价。名义 1M 不等于「1M 都好用」。[2]
token = 字符 = 词 不同维度。中文 1 token ≈ 1~2 字，英文 1 token ≈ 0.75 词。[1]
Prompt caching 只是省钱 同时降本和加速，命中长 prefix 时可降本约 10×、首 token 延迟下降约 5×。[5]
「上下文」指整段对话 不只对话，是系统提示 + 历史 + 工具结果 + 检索内容的拼接。
信息放在哪里都一样 不是。Lost-in-the-Middle 已多次复现，关键信息放首尾更稳。[3]
