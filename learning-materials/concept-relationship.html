Agent、大模型的上下文、Skill —— 三角关系

60 秒速读 Agent 是会行动的演员，上下文 是它当下能看到的全部台面，Skill 是它按场景取用的剧本。上下文决定 Agent 这一刻「知不知道、能用啥」，Skill 决定它「在什么场景该怎么演」。三者一起，才让 AI 从「回答问题」升级为「在合适的时机、按合适的方式、做出合适的事」。

一句话关系

Skill 告诉 Agent 「在 X 场景下，按 Y 步骤，产出 Z 格式」； 上下文 决定 Agent 「这一步能不能看到所需的历史、工具、文档」； Agent 把它们串成一个能自主决策和执行的循环。

概念对比表

维度 Agent（智能体） 大模型的上下文 Skill（技能）
本质 一个能自主决策和执行的运行系统 一次请求中模型能看到的全部 token 一份带元数据的可复用提示词/脚本包
谁拥有它 通常由开发团队/Agent 框架搭建 由调用方每次请求构造 由 Skill 作者创建并提交到项目/用户/市场
解决什么问题 把判断和执行合到一起 把当下最相关的信息喂给模型 把一次性对话沉淀成可复用资产
出问题会怎样 死循环 / 工具调用失败 / 越权 关键信息被挤掉 / context rot 误调用 / 越权 / 提示词注入
类比 会按剧本演的演员 演员此刻能看到的台词和道具 一份按场景分类的剧本

重点 1：上下文如何影响 Agent 的工作

Agent 是个循环系统：观察 → 决策 → 行动 → 再观察。每一步都依赖「当下能看到的全部上下文」。所以上下文对 Agent 的影响体现在四个层面：

  1. 决定决策质量：上下文里如果漏掉了关键工具返回，Agent 就会基于错误信息做下一步判断；如果塞了太多无关信息，又会触发 context rot，决策变差。Anthropic 2025 年的研究指出，「装得多」≠「记得好」，所以上下文的选择本身就是 Agent 工程质量的一部分。
  2. 决定可执行范围：Agent 能调用哪些工具、能读哪些文件，全都在系统提示和工具 schema 里——这些都占 token。工具集大 = 系统提示大 = 留给对话/历史的预算少。所以「工具设计」也是上下文工程。
  3. 决定成本与延迟：每次请求按 token 计费，1M 窗口的全量调用在 Anthropic 长上下文模型上比 200K 贵几倍，且长上下文首 token 延迟更高。Agent 一旦陷入「全量塞 → 重新问 → 全量塞」的循环，钱包和速度都吃不消。
  4. 决定可控性：工具结果、扩展思考块、对话历史——这些都是「可注入」到上下文的载体，也是提示词注入攻击的主要目标。所以 Agent 工程上需要做：① 工具输出做白名单/截断；② 系统提示和用户内容严格隔离；③ 关键操作前要求人类确认。

重点 2：Skill 如何沉淀可复用的任务知识

如果说上下文是「一张白纸」，Agent 是「拿着白纸思考的演员」，那 Skill 就是「剧本集」。它的沉淀逻辑是：

沉淀什么

  • 角色定义：你希望 AI 扮演谁、用什么口吻、关注什么
  • 步骤规则：固定的 3-5 步流程（如「先查 → 再算 → 再写」）
  • 输出格式：JSON 字段、Mermaid 图、HTML 模板
  • 边界护栏：不该做什么、遇到 X 该怎么办
  • 外部资源：可选的脚本、模板、引用文档

怎么沉淀

  1. 把当前对话里调好的提示词整理成 SKILL.md（YAML 元数据 + Markdown 正文）。
  2. 放到 .workbuddy/skills/<name>/，连同脚本/模板一起 commit。
  3. 下次同类任务，AI 自动按 read_when 加载它；不再需要重写一遍提示词。

为什么是「Skill」而不是「prompt 文件」

普通 prompt 文件是一次性的——人记得住才能复用。Skill 多了一层「机器可读的元数据」：read_when 让 AI 知道什么时候调它，summary 让搜索能定位它，title 让 UI 能展示它。所以 Skill 更像「面向 AI 的 API 文档」，而 prompt 只是「人写给人看的备忘录」。

我的个人判断（robin01-sw）

  • 不要把 Skill 神化。一个好的 Skill 是把「我已经验证过的最佳实践」固化下来，不是把「也许有用的话术」写进 YAML。第一次写 Skill 时，通常你会反复迭代 3-5 次提示词才能稳定——这是正常的，别跳过这一步。
  • 上下文是 Agent 最贵的资源。在 Agent 设计里，工具数量、系统提示长度、对话保留策略，每一项都要算 token 账。我倾向于「工具越少越好」「系统提示越短越好」「工具结果先在工具侧切片」，而不是「让模型自己筛选」。
  • 三者的耦合点是人。Skill 写得再细，如果调用者不知道怎么把它放进上下文，Agent 也不会用。WorkBuddy 的项目级 Skill 路径就是把这个耦合点变成「仓库约定」——clone 项目的人自动获得这套工作流。
