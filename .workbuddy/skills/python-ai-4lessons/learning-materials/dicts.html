字典

字典用名字存数据，取值靠键，不靠位置。

花括号写，每项是「键: 值」一对。d['标题'] 按键取值；键不存在会报 KeyError， 改用 d.get() 就不会。[1] items() 能一次拿到键和值。字典能装列表，列表也能装字典。

💡 通俗理解 · AI 辅助整理 · 本人已核查

字典像一张采访本上的信息卡：不是按「第几行」找内容，而是按栏目名找——写「标题」就翻到标题那一格。卡片上每一格都写着栏目名和内容，这就是「键」和「值」。好处是顺序怎么换都不影响，因为找东西靠的是名字。代价是栏目名不能重复：写两个「标题」，后面的会顶掉前面的。名字还得选不会变的，列表不能当键。

学习目标

  • 能解释"键值对"是什么意思，以及它和列表按位置取值的根本区别。
  • 能区分 d['键'] 与 d.get('键') 在键不存在时的不同结果。
  • 能写出把一条稿件的标题、记者、日期、关键词存入一个字典的代码。
  • 能判断一份数据该用列表装还是用字典装，并说出判断依据。

核心问题

用列表按位置取和用字典按键取，差别真有那么大吗？
差别的核心是代码能不能自解释。record[3] 这样写，读过这段代码的人 必须回头去数字段顺序；record['关键词'] 一眼就知道取的是什么。 更实际的是容错：字段顺序一换，按位置取的代码会悄悄取错值且不报错， 而按键取值完全不受影响。[1]
d['某某'] 报 KeyError 是怎么回事？
说明这个键在字典里不存在。官方教程写得很清楚：通过下标操作提取不存在的键的值会引发 KeyError；要避免这种错误，可以改用 get() 方法， 它在键不存在时返回 None（或者你指定的默认值）。[1] 两种写法各有用途：d['键'] 适合"这个键必须要，没有就是数据有问题"； d.get('键', '未知') 适合"缺了就按缺的处理"。
keys()、values()、items() 分别拿到什么？
keys() 拿到全部键，values() 拿到全部值， items() 拿到全部"键值对"，可以一次拆成两个变量用。[7] 官方教程里打印电话簿的例子就写成 for name, phone in table.items():， 每一轮 name 得到键、phone 得到值。 另外，判断某个键在不在，直接写 '记者' in d 就行， 默认查的是键不是值。[1]
字典和列表能互相装吗？
能，这是它们最有用的一点。字典里可以放列表，比如一条稿件的 '关键词': ['改造', '竣工', '老旧小区']； 列表里也可以放字典，比如 200 条稿件就是一个列表，每一项是一个字典。 这个组合正是概念 10"特征与标签"要用的形状：列表装多条样本，字典描述单条样本。 顺带说一句，列表不能当字典的键，因为它是可变对象。[3]
什么叫"结构化数据"，为什么它重要？
结构化数据就是每个字段都有固定名字、固定含义的数据， 而不是一段需要人去读的整块文字。 一段 '王某某，男，45岁' 是文字；把它变成 {'姓名': '王某某', '性别': '男', '年龄': 45} 才是结构化数据。 重要性在于：只有结构化了，才能统计、比对、批量处理，也才能交给机器。 新闻行业早就在做这件事——IPTC 的 ninjs 标准用 JSON 表示一条新闻， 字段名固定为 headlines、by、contentCreated、subjects 等。[6]

结构化解释

是什么

字典是键值对的集合，用花括号写，逗号分隔。[1] 和以整数为索引的列表不同，字典是以键来索引的， 主要操作就是"用键存值、用键取值"。三条规则要记住： 键必须唯一（用已有的键再存一次，旧值会丢失）； 键必须是不可变对象（字符串、数字都可以，列表不行）； 键的存放顺序和取值无关，所以不能靠"第几项"去取。

为什么

三个原因。第一，代码要能自解释。record['标题'] 和 record[0] 在功能上可能等价，但在三个月后回头读的时候完全不是一回事。 第二，容错：采访记录多了字段、少了字段、换了顺序， 按键取值的代码不需要改，按位置取值的代码会静默出错。 第三，这是通往机器学习的形状：概念 10 里的"一条样本 = 一组特征 + 一个标签"， 落地就是字典；一批样本就是列表里装字典。 换句话说，字典不只是"另一种容器"，它是把新闻变成数据的那个关键一步。

怎么工作

  1. 建字典：record = {'标题': '……', '记者': '李某某'}，空字典写作 {}。
  2. 取值：record['标题'] 直接取，键不存在报 KeyError； record.get('版次') 键不存在时返回 None， record.get('版次', '未标') 可以指定默认值。[1]
  3. 判断与增改：'记者' in record 判断键在不在； record['版次'] = 'A2' 既可以是新增，也可以是修改 （键已存在时旧值被覆盖）。[1]
  4. 遍历：record.keys() 取全部键，record.values() 取全部值， record.items() 一次取键和值。[7][2]
  5. 嵌套：值可以是列表（关键词），也可以是另一个字典（比如"来源"里再分"媒体名"和"链接"）。
  6. 键的约束：字典靠键算出值的存放位置，所以键必须不可变； 用列表当键会报 TypeError: unhashable type: 'list'。[3][4]
对比项列表：按位置取字典：按键取
取值写法record[0]、record[3] record['标题']、record['记者']
字段顺序变了全部取错，而且不报错——最难发现的错误 不受影响，照样取得到
新增一个字段排在它后面的位置全部要重数一遍 多写一行就够
适合装什么一列同类东西：一批标题、一批关键词 一条有多个字段的记录：一篇稿件、一位采访对象

应用案例

第三周新增了一个字段，两百条记录的代码全部要改。 2026 年 6 月，某省报数据新闻组要把见报稿件录成一个文件，交给后面的选题分析用。 第一版用的是列表，一条稿件存成一个列表： ['A小区改造工程今日竣工', '李某某', '2026-06-18', '城建']。

问题出现在第三周。编辑要求每条稿件再加一个"版次"字段，也就是从 4 项变成 5 项。 所有按位置取值的代码都要重数一遍；更麻烦的是，翻回两周前的代码， 没有人能立刻说清 record[3] 到底是"栏目"还是"关键词"。 按位置取值的最大风险就在这里：取错了也不会报错， 它只是安静地把另一个字段的值交给你。

第二版改成字典之后，同样的问题不再出现：record['标题']、 record['记者']、record['日期']，字段换了顺序照样取得到； 新增"版次"也只是多写一行 record['版次'] = 'A2'。[1] 三个月后另一位同事接手，读代码时不需要任何额外说明。

示意（推演场景，非公开报道）

上面的单位、稿件与字段为教学推演。 但"用列表按位置存记录、后来加字段"是数据整理里最经典的一类返工， 真实项目中出现得非常频繁。这也是为什么行业标准会把字段名固定下来—— IPTC 的 ninjs 用 JSON 表示一条新闻，标题、署名、时间的字段名分别是 headlines、by、contentCreated，一写就用十几年。[6]

概念辨析

邻近概念 与本概念的区别 一句话区分点
列表（概念 03） 列表按位置索引，字典按键索引。 列表适合"一列同类东西"，字典适合"一条有多个字段的记录"。 两者可以互相嵌套，合起来才是真实数据的形状。 知道"第几位"就用列表，知道"叫什么"就用字典。[1]
JSON JSON 是写进文件或通过网络传输的一种文本格式， 长相和字典很像（花括号、键值对、双方括号的列表）； 字典是程序运行时的对象。两者可以互相转换。 字典是内存里的东西，JSON 是可以存下来、发出去的那份文本。
键的唯一性
与不可变性		 同一个键只能出现一次，后面写的会覆盖前面的；键还必须是不可变对象， 所以字符串、数字可以，列表不行。原因在于字典靠键算出值的存放位置。 键既是"名字"，也是"门牌号"，所以不能重复、不能变。[3]
行业元数据标准
（ninjs）		 字典解决的是"一条记录在程序里怎么表示"， ninjs 解决的是"整个行业约定这条记录该有哪些字段"。 它用 JSON 表示新闻，字段名固定为 headlines、by、 contentCreated、subjects 等， 2013 年发布，现在已是 3.0 版。[5] 字典是技术手段，元数据标准是行业约定：前者实现，后者定义"什么算完整的一条记录"。
