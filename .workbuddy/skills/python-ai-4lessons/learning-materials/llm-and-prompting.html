大模型与提示

概念卡 16 前置：函数 · 文件读写 · 情感分析 8 道分层自测 8 条可核查来源
60 秒速读

调大模型 API，就是发一个 HTTP 请求、拿回一段 JSON。

返回的 JSON 里装着模型的回答，用 Python 解析就能取用。 提示词要说清角色、任务、输入和期望的输出格式；同一句话问两次答案可能不同。 它会一本正经地编内容，所以结果必须校验。[5]

💡 通俗理解 · AI 辅助整理 · 本人已核查

调用大模型 API 像给一位外包顾问寄表格：你写好一张单子（他扮什么角色、要做什么、材料是什么、按什么格式交回来），寄出去，收回一张标准表格。这位顾问很能干，但单子可能每张换一个收件人，同样的话两次回的措辞可能不同；他偶尔还会一本正经地填上不存在的数字。所以表格拿回来必须先核对，再进你的稿子。

学习目标

  • 能解释调用大模型 API 时，代码层面实际发生了什么。
  • 能说出提示词必须交代清楚的四个要素，并为其中一个写出具体例子。
  • 能说明为什么模型的输出必须校验，以及校验分哪几关。
  • 能说出本地模型与大模型在同一条流水线里该怎么分工。

核心问题

调用大模型 API，代码层面到底发生了什么？
就是一次普通的网络请求，和你用代码去下载一个网页没有任何本质区别。 Python 官方文档对 urllib.request 的说明是：它定义了一组用于 打开 URL（主要是 HTTP）的函数和类， 并且 urlopen 返回的对象可以当上下文管理器用， 带有 url、headers、status 三个属性。[2] 区别只在两处：你要用 POST 把提示词发过去，对方返回的是一段 JSON 文本，而不是一个给人看的网页——所以这正好用得上第 2 课的函数与字典。[1]
API key 应该放在哪里？
放在环境变量里，代码从环境变量读，绝不写进 .py 文件再提交到 Git。 原因很直接：Git 会保留每一次提交的历史，key 一旦进去，就算后来删掉，历史里还在； 任何能看到这个仓库的人都能拿它去消耗你的额度。 正确做法是代码里写 os.environ["LLM_API_KEY"]， 仓库里只留一份说明写清"需要设置哪个环境变量"。 这也是成本意识的一部分：key 泄露和忘关循环，是新手最常遇到的两笔意外账单。
提示词要写清哪几件事？
四件事：角色（你希望它以什么身份来回答）、 任务（要它做什么）、输入（要处理的材料）、 期望的输出格式（按什么结构交回来）。 公共部门发布的提示写作指南给出的模板正是这四段：ROLE / INSTRUCTIONS / AUDIENCE / FORMAT， 并说明清楚、结构化的提示会显著提高输出的准确性； 含糊或不完整的提示则容易得到空泛、跑题的回应。[4] 新闻场景里还要加一条：把"拿不准就说拿不准"写进去， 并要求它给出判断依据。
为什么同一句话问两次，答案可能不一样？
因为它是按概率逐字生成文本的，不是查表。 所以单次输出不能当作稳定事实，更不能当作可复现的测量结果。 这对新闻工作的直接含义是两条：一是关键结论不要依赖一次调用， 要留记录、能重跑；二是它写下的每一句可核查的话都要回到原始材料核对。
它会不会编？编了怎么办？
会，而且这是被正式写进风险清单的一件事。 美国国家标准与技术研究院（NIST）在 2024 年 7 月发布的生成式 AI 风险文件里， 把"生成看似自信却错误或虚假的内容"（也就是通常说的"幻觉"） 列为十二类风险之一，并配套给出两百多条管理措施。[5] 怎么办？把校验当成流水线上固定的一关，而不是可选的礼貌： 结构对不对、取值在不在允许范围、内容能不能在原文里找到依据。 三关都过不了的，交给人。

结构化解释

是什么

大模型 API（应用程序接口）是一种用程序而不是用对话框来使用大模型的方式。 你发一次 HTTP 请求，请求体里装着提示词和要处理的文本，对方返回一段 JSON， 你再从 JSON 里把答案取出来。[2] 用 requests 库的话，发 POST 并直接以 JSON 形式提交数据只要一行： requests.post(url, json=payload)；响应对象上有 .json() 方法， 能把返回内容解析成 Python 的字典。[3] 而"字典"正是第 2 课就学过的容器——从 API 里取数，本质就是从一个嵌套字典里取数。

为什么

因为它的强项和它的短板是同一件事的两面。 强项在理解上下文：反讽、双重否定、需要解释理由的判断，它比本地分类器做得好。 短板在不可复现与不可控成本：按量计费意味着跑一万条和跑五千条价钱不同， 而同一个提示两次可能给出不同措辞的回答。 新闻行业的基本共识也落在这两条上：《Paris Charter on AI and Journalism》要求 人类决策保持在新闻工作的中心、任何对内容有重大影响的 AI 使用都应向受众披露， 媒体对已发布内容承担编辑责任；[6] 国际调查报道的实践则把它总结成一句更朴素的规矩—— 机器负责把大堆分成小堆，人负责判断小堆里哪一条是新闻， 而且"每一步都有记者在回路中"。[7]

怎么工作

把一次调用拆开，你会看到五个动作，其中三个是人该负责的：

  1. 从环境变量取 key 和接口地址，不要硬编码进代码。
  2. 组装提示词：角色、任务、输入、期望的输出格式，缺一样都会让结果变得难用。[4]
  3. 发请求。用 requests.post 提交，先 raise_for_status() 确认请求成功， 再 .json() 解析。官方文档特意提醒过： r.json() 能成功解析并不代表这次响应是成功的—— 有的服务器在失败的响应里也会返回一个 JSON 对象（比如 HTTP 500 附带的错误详情）， 所以要用 raise_for_status() 或 status_code 来判断。[3]
  4. 校验结果。JSON 与 Python 之间的对应关系是明确的： object 对应 dict、array 对应 list、string 对应 str、number 对应 int 或 float、 true / false 对应 True / False、null 对应 None。[1] 解析成功后，还要检查字段名对不对、取值在不在允许的清单里。
  5. 分工与复核。全量数据用本地模型跑，疑难样本交给大模型， 两者的分歧点由人核对——这也是调查研究里的通行做法。[7]
import os, requests

def ask_model(prompt, text):
    url = os.environ["LLM_BASE_URL"] + "/chat/completions"
    key = os.environ["LLM_API_KEY"]        # 从环境变量读，不写进代码
    payload = {
        "model": "your-model-name",        # 用你自己账号里的模型名
        "messages": [
            {"role": "system", "content": prompt},   # 角色 + 任务 + 输出格式
            {"role": "user",   "content": text},     # 输入
        ],
    }
    headers = {"Authorization": "Bearer " + key}
    r = requests.post(url, json=payload, headers=headers, timeout=60)
    r.raise_for_status()                   # 先确认请求成功
    return r.json()                        # 再解析成字典

应用案例

真实的规定：不确定性的来源被写进了官方文件。 2024 年 7 月 26 日，美国国家标准与技术研究院（NIST）发布《AI 风险管理办法：生成式 AI 剖面》 （NIST AI 600-1），用十二类风险加两百多条对应措施来管理生成式 AI， 其中一类就是"生成看似自信却错误或虚假的内容"， 文件里用的词是 confabulation，也就是通常说的"幻觉"。[5] 同年 11 月 10 日发布的《Paris Charter on AI and Journalism》则从新闻行业一侧提出要求： 人类决策必须保持在中心位置，任何对内容有重大影响的 AI 使用都应披露， 媒体对发布出去的每一条内容承担编辑责任。[6] 两条放在一起看，"返回结果必须校验"就不是一句谨慎的忠告，而是行业的基本操作要求。

示意案例（推演，非公开报道）

某编辑部想用大模型把 5000 条读者留言按八个议题分类，再据此做一张图表。

  • 第一次的做法：写了一句"请判断下面这条留言属于哪个议题"，循环跑了 5000 条， 程序没报错，把结果直接汇总画图。问题出在两个地方：返回的是自由文本而不是结构化字段， 得靠字符串切开才能取类别；抽取的 100 条里，有 7 条把反讽当成了正面表述。
  • 改过之后的做法：提示词补上角色、任务、输入和输出格式 （要求只返回 {"topic": "...", "confidence": 0.0-1.0, "reason": "..."}）， 并在提示里写明"拿不准就把 confidence 给低、并在 reason 里说明"。 程序加了三道校验：能不能解析、topic 是否在八类清单里、confidence 是否在 0 到 1 之间。 校验不过的 63 条单独列出交给人；另外每周抽 50 条人工复核，记录不一致的样例。
  • 关于成本用的是"分工"而不是"全上"：先用本地分类器跑完全量， 只把把握度最低的那一批交给大模型，再由人核对两者的分歧点。 这样既有可复现的基线，又保留了大模型在疑难样本上的判断力。

这个案例是推演的，用来把五个动作串成一条线。具体的字段名、模型名与阈值 需要按自己账号和语料实际情况来定；本卡不推荐任何具体厂商或型号。

概念辨析

邻近概念 与本概念的区别 一句话区分点
本地分类模型
（文本分类）		 本地模型训练一次可以反复跑，结果稳定、单条成本趋近于零，但只认自己学过的用词习惯；大模型懂上下文、能给理由，但成本随调用量增长、同一提示两次回答可能有出入。 本地模型是"自己养的狗"，听话但不机灵；大模型是"请来的顾问"，机灵但按次收费。[7]
人工标注的规则表 两者都是"交给执行者的一套明确规则"：人工标注的规则写给人看，提示词写给模型看。共同要求也一样——规则必须具体到"换一个人、换一次调用也能得到同样的判断"。 规则表是给人看的提示词，提示词是给模型看的规则表。[8]
在网页对话框里直接问 对话框里是人手动问、人眼看答案，格式随意；API 是让程序自动批量调用，产出必须能被程序解析，所以输出格式必须写死。 对话框适合问一次，API 适合问五千次——后者才需要把校验写成代码。[2]
模型幻觉 普通的分类错误是"在给定选项里选错了那个"，幻觉是"生成了根本不在选项里、或者原文里根本没有的内容"。前者靠调阈值和补标注改善，后者只能靠校验和核对拦住。 选错是判断问题，编出来是编造问题——后者必须回到原始材料核对。[5]
